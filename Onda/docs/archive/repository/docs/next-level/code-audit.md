# Next Level: code reuse audit

2026-10-12 · Local branch `next-level` · Audited HEAD `5e5caca`

**Recommendation:** reuse the October execution and durable-command mechanisms, authenticated parent conversation transport, and selected editor patterns. Replace the profile's meaning and write contract before presenting it as evidence-grounded developmental working notes. The current product can accumulate and edit family facts; it cannot explain, qualify, revise, or reliably forget individual inferred claims.

This is an exploration report, not a pivot decision or implementation authorization. The working hypothesis is a conversation-first, parent-only coach with a small set of editable working notes: what the parent observed, a tentative interpretation, what they tried, and what happened. Administrative planning and generic content are outside this proposed core. Neuroscience differentiation is unproven. Repository access establishes neither code ownership nor rights to reuse content, prompts, illustrations, or named experts' material.

## Actual mechanisms and gaps against the profile hypothesis

### 1. The existing profile is a current snapshot, not a developmental record

`FamilyProfile.children` is a dictionary keyed by child name (`mvp-backend/app/profiling.py:153`). Parent and child records hold scalar strings and lists. They have no per-claim source message, author, observation date, confidence, review state, revision, superseded-by relation, or deletion marker. The durable JSON blob gets an `updated_at` value (`mvp-backend/app/duckdb_storage.py:1448`); that is not a chronology of observations.

There are useful raw ingredients: stress patterns, de-escalation successes/failures, goals, triggers, calming strategies, school context, sleep and recent changes (`mvp-backend/app/profiling.py:54`, `mvp-backend/app/profiling.py:73`, `mvp-backend/app/profiling.py:126`). But `neurodiversity` combines “diagnosed/suspected” in one string and `learning_profile` is also an unconstrained string. There is no representation separating a parent's observation from the model's interpretation or from a clinician's reported finding. A richer form over these same fields would not establish evidence grounding.

**Required change:** introduce individually addressable notes with provenance and state. Keep parent observations distinct from hypotheses and externally sourced explanations. Do not convert a single difficult evening into a persistent child trait.

### 2. Extraction commits facts silently; correction semantics are asymmetric

The coach is instructed to record what was said or “clearly implied,” keep doing so, and not tell the parent (`mvp-backend/app/agent.py:275`). Both coach and onboarding import the shared update schemas (`mvp-backend/app/agent.py:56`, `mvp-backend/app/onboarding_agent.py:17`). Their tools remove `None` fields before mutation (`mvp-backend/app/agent.py:340`, `mvp-backend/app/agent.py:358`). List updates merge; empty lists do nothing (`mvp-backend/app/profiling.py:6`). Therefore a conversation tool cannot clear an old list simply by sending `[]`, or clear a scalar with `null` through this wrapper. Editors have replacement semantics (`mvp-backend/app/profiling.py:197`).

The October implementation improves *delivery*: it reads durable truth in an isolated service, commits, then publishes the cache (`mvp-backend/app/services/profiles.py:79`, `mvp-backend/app/services/operations.py:195`). It does not improve whether the extracted assertion is justified or whether a correction supersedes an older claim.

**Required change:** candidate-note creation, parent accept/edit/reject, explicit supersession and forgetting. Receipts deduplicate a repeated tool-call ID; a new model call with a new ID is intentionally a new operation (`mvp-backend/app/services/operations.py:1`). They do not deduplicate repeated client messages or semantically equivalent observations.

### 3. Name keys and deletion undermine correction

A PATCH to `/profile/kids/Rowan` with `{"name":"River"}` changes the object's name without changing its `Rowan` dictionary key (`mvp-backend/app/server.py:1683`, `mvp-backend/app/profiling.py:204`). A later agent update addressed to `River` creates another child (`mvp-backend/app/profiling.py:188`). iOS intentionally sends the original key while editing the displayed name (`mvp/MVP/ProfileEditorViews.swift:487`, `mvp/MVP/ProfileEditorViews.swift:586`); web does the same (`mvp-backend/parent-dashboard/src/pages/Profile.tsx:61`). This is a current mechanism, not just a stale context-doc warning.

Child removal deletes the profile and a specific set of child-agent tables, with cleanup exceptions logged and tolerated (`mvp-backend/app/server.py:1700`, `mvp-backend/app/duckdb_storage.py:2695`). That path does not purge the parent's transcript/checkpoints, invalidate all relevant agent context, or create a child tombstone. The child updater creates any missing name. Consequently, old conversation context can be used to recreate a removed child; the pure profile-service recreation was reproduced synthetically, while the full model sequence was not run. The iOS claim that it removes “everything saved about them” is broader than this cascade (`mvp/MVP/ProfileEditorViews.swift:565`).

**Required change:** immutable child IDs; revision-aware note edits; explicit forget semantics across projections and context; no automatic recreation from retained history.

### 4. HTTP editing and seeding lag the hardened tool path

Parent/kid PATCH mutates the global profile cache before `persist_state` (`mvp-backend/app/server.py:1677`, `mvp-backend/app/server.py:1694`). Persistence locks snapshot publication and checks family fences, but begins after that cache mutation (`mvp-backend/app/server.py:440`). Storage failures propagate (`mvp-backend/app/duckdb_storage.py:1467`), so the route should fail rather than return success; however, there is no rollback of the preceding cache mutation. A failed save can thus leave a visible in-memory change, and editor/agent concurrency needs testing. There is no expected-revision/ETag check to reject a stale editor overwriting a newer fact.

Seeding also changes the cache first, writes planning rows, then persists the profile (`mvp-backend/app/server.py:1536`, `mvp-backend/app/server.py:1576`, `mvp-backend/app/server.py:1614`). Its retry deduplication is by activity name + child name, not an atomic idempotent onboarding command. Keep the client retry lesson, not this server composition.

**Required change:** one transactional service for agent, editor and onboarding note writes. Publish cache only after commit; return a revision; retry a stable operation ID without repeating effects.

### 5. Cross-surface schemas still differ

Static AST comparison found these profile fields absent from the shared agent tool schemas (`mvp-backend/app/profiling.py:34`, `mvp-backend/app/profiling.py:99`, `mvp-backend/app/services/profiles.py:8`, `mvp-backend/app/services/profiles.py:42`):

- Parent: `coach_personality`, `coach_voice`, `education_style`, `family_activities`, `focus_topic`, `self_care_tasks`, `avatar_key`.
- Child: `dislikes`, `goals`, `school_style`, `name`, `avatar_key`.

`avatar_key` should be excluded and `child_name` intentionally serves as the tool's name input. The remaining differences show that a shared coach/onboarding schema is not complete parity with storage and editors. iOS also lacks several newer parent fields in its DTO, including `focus_topic` and `self_care_tasks` (`mvp/MVP/ProfileService.swift:8`). Web grade-band choices are broad bands (`mvp-backend/parent-dashboard/src/pages/Profile.tsx:16`), while the onboarding prompt asks for Pre-K/K/1–12/N/A (`mvp-backend/app/onboarding_agent.py:86`).

**Required change:** a versioned note contract exercised through backend, iOS and web, including explicit clear, reject, rename, optional fields and conflict responses. Do not silently ignore an unknown claim field as `_apply_update` currently does.

### 6. Personalization exists; evidence retrieval and scientific validation do not follow from it

The agent prompt incorporates the entire nonempty profile, saved-item signals, household context, ranked articles and the catalog (`mvp-backend/app/agent.py:388`, `mvp-backend/app/agent.py:434`). Cache rebuilding compares this context and the prompt (`mvp-backend/app/agent.py:471`). This provides personalization across later turns. It is not a retrieval policy that selects relevant, current, parent-approved observations and excludes disputed ones. A graph's system prompt is assembled when the graph is built; refreshing the profile cache during a tool call does not itself rebuild the current graph.

The catalog contains titles/subtitles and links, not a claim-to-source evidence ledger (`mvp-backend/app/content.py:263`). Search is available and the prompt requests citations (`mvp-backend/app/agent.py:261`), but there is no checked citation-support relationship in the inspected profile/write path. `soul.md` tells the coach to internalize named frameworks without citation; the onboarding prompt invokes named experts (`mvp-backend/soul.md:35`, `mvp-backend/app/onboarding_agent.py:95`). These are prompting choices, not demonstrated neuroscience expertise, a validated developmental model, or proof of content rights.

The October scripted-model tests explicitly exclude parenting quality, actual model tool choice, latency and cost from their claims (`mvp-backend/tests/agents/test_parent_scenarios.py:1`). Preserve them as engineering regressions. Add separate expert-reviewed, synthetic quality scenarios for grounded suggestions, uncertainty, contradictions, sensitive labels and referral behavior. Any future claim of differentiated outcomes needs independent evidence beyond code and prompt wording.

**Proposed retention direction:** separate durable, parent-approved notes from raw conversation. Make transcript retention an explicit choice with a bounded policy, and retain only the minimum parent-approved evidence excerpt when a note needs provenance. If that excerpt is erased, show “source removed” or remove the dependent note; never pretend a missing source still verifies it. Exact periods, backup rules and provider terms remain decisions, not facts established by this audit.

## Tenant isolation and execution reuse limits

1. **Text/profile isolation has concrete application checks.** `/chat` checks the claimed user against the bearer; profile PATCH derives the owner from the bearer; thread reopen checks that the conversation belongs to that user's stored state (`mvp-backend/app/server.py:1121`, `mvp-backend/app/server.py:1668`, `mvp-backend/app/coach_threads.py:285`). Tools bind the tenant in closures; trusted run context is not a model argument (`mvp-backend/app/agent.py:331`, `mvp-backend/app/agent_runtime/context.py:1`). Receipt lookup scopes by user and thread, and reference validation checks resource ownership (`mvp-backend/app/services/operations.py:111`, `mvp-backend/app/services/operations.py:144`). These are valuable guards, not a database-enforced tenant policy.
2. **The owner is an account `user_id`.** Do not assume a household member, co-parent, or shared child implies access to coaching notes. Household reads use the authenticated owner's profile (`mvp-backend/app/household.py:427`), and current profile writes have no per-note audience model. The proposed default should be private to the parent account, with any later sharing explicit per object.
3. **Legacy auth remains permissive by source default.** `/auth/issue-token` is unauthenticated and enabled by default; it blocks accounts with linked sign-in identities but issues for unclaimed identifiers (`mvp-backend/app/server.py:702`). Legacy token acceptance also defaults on (`mvp-backend/app/auth.py:71`). JWT validation has a development fallback if the configured signing secret is absent (`mvp-backend/app/auth.py:37`). No deployed settings were inspected. Reuse must include explicit fail-closed launch configuration and tests; source defaults are not sufficient for sensitive notes.
4. **Voice uses a different trust boundary.** The token route derives `user_id` from parent auth (`mvp-backend/app/server.py:2392`), but the callback checks a provider shared secret then trusts `elevenlabs_extra_body.user_id` and `thread_id` (`mvp-backend/app/parent_convai_endpoint.py:68`). The code shown does not cryptographically bind that callback identity to the original parent session. Whether a client can alter those fields through the deployed provider is unverified. Require a short-lived server-signed binding or server-side session lookup before carrying private notes through this path.
5. **String namespaces are not an ownership registry.** Text keys are `{user}:parent[:conversation]`; voice is `{user}:{thread}` (`mvp-backend/app/agent.py:118`). An arbitrary voice thread can alias a text suffix within that user. Reserved/colon-containing users make legacy ownership ambiguous. October purge deliberately fails closed on ambiguous/overlapping owners (`mvp-backend/app/checkpointing.py:376`, `mvp-backend/app/checkpointing.py:427`). Keep these guards and move new records toward explicit owner columns/validated IDs, rather than expanding string conventions.
6. **Concurrency guarantees are single-process.** Conversation locks are event-loop local (`mvp-backend/app/agent_runtime/sessions.py:18`); family admission fences are also process-local (`mvp-backend/app/agent_runtime/service.py:36`). Durable generation checks protect scoped database writes, but this is not a multi-replica lease design. Replicas require a separate ownership design and tests.
7. **Feature flags do not mean the old path has no protections.** Shared runtime and COS active-conversation flags default off (`mvp-backend/app/agent_runtime/policies.py:5`). The legacy chat path still uses ownership and durable run scope (`mvp-backend/app/server.py:486`). Voice cancellation applies specifically to `parent_voice`, not all surfaces (`mvp-backend/app/agent_runtime/cancellation.py:28`). Tests must cover both adapter modes until one is removed.
