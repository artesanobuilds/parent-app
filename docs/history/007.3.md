# 007.3: Data sync incident, recovery, and operational tooling

**Date:** Late March – April 2026 (between the Railway launch and session 008)
**Objective:** Recover from a production-sync incident that wiped local user data, harden the sync workflow against repeat failures, and capture the lessons.

> Reconstructed from memory files `debugging_data_sync.md`, `debugging.md`, and `local_llm_setup.md`. No commits in this window; this entry exists primarily to capture an operational incident and the resulting safety changes.

## Decisions
- **`local-storage/<user>/` JSON is the source of truth for user data**, not the parquet snapshots in production. Production starts empty and only has data for users who chatted there; running `sync-data.sh` against a fresh prod will overwrite a fuller local copy.
- **Always redeploy after any local data recovery** so the restored `mvp.parquet` lands in the Docker image's `seed-data/` and survives future deploys.
- **Don't chain naive sleep loops to wait on prod** — let the user drive timing for sync/deploy operations (logged as `feedback_no_polling.md`).

## Implementation

### Recovery path (proven during the incident)
1. `python migrate_json_to_duckdb.py` — rebuilds `data/mvp.duckdb` and parquet snapshots from `local-storage/Miguel/`, `local-storage/Julio/`, `local-storage/Pepe/` JSON files.
2. Verify counts in DuckDB.
3. `cd mvp-backend && railway up` — bake the restored parquet into a fresh image so the Railway volume seeds correctly on next boot.

### Hardening
- `entrypoint.sh` updated to compare file sizes and replace volume files only when the seed is **larger** than the volume copy (avoids the seed clobbering live data going forward, while still letting a deliberate redeploy push corrections).
- `tools/sync-data.sh` — added `--watch` mode (30-minute interval) and an audit log at `data/.sync-audit.log`.

### DuckDB single-writer constraint (logged in `debugging.md`)
- Cannot run `migrate_content_to_duckdb.py` while uvicorn is holding the same DB file. Workaround: run with `--db-path data/mvp_migrate.duckdb` to use a separate DB; the parquet exports are what matter for bootstrap and they're shared.
