# Iteration 2 code audit: helping the parent adapt

2026-10-13 · Branch `next-level` · Source baseline `6560a2e`

**Final revision incorporating all three supplied research reports, 2026-10-13.** Code findings and research reconciliation are complete within this local audit. The episode contract and reflection dimensions are proposed designs, not validated constructs or demonstrated outcomes. Instrument licensing, population-specific interpretation and product benefit require separate work; none is inferred from code or vendor marketing.

## Recommendation and scope

Reuse the parent context fields, durable command infrastructure, conversation transport and correction UI patterns. Introduce a small, source-attributed **relationship episode** rather than extending a child-trait profile. Its purpose is to help the parent consider their capacity, interpretation, response, boundaries and repair in a particular interaction. Understanding the child informs what the parent chooses to do; changing or controlling the child is not the optimization target.

The existing system is not child-only: it already collects substantial parent context. What it lacks is a representation connecting that context to a specific interaction without turning either participant into a fixed type. The new unit should pair a parent's account of the child's observable actions with the parent's own reported state and actions, preserve what remains unknown, and support a small parent-chosen adjustment. “Paired” means two sides of one reported interaction, not independently verified accounts from two people.

Therapeutic alliance is an unvalidated analogy here. Do not calculate an alliance, attachment, relationship-health, parenting-quality or developmental score from chat, including a qualitative tier that functions as a disguised score. The dimensions below are optional reflection prompts, not a validated scale, diagnostic instrument or causal model. Neuroscience differentiation and ownership/content rights remain unresolved.

**Construct boundary:** Parenting Alliance Measure concerns co-parent cooperation; Working Alliance Inventory concerns therapy/helping relationships. Neither validates an ordinary parent–child alliance score (`docs/next-level/iteration-2/research/parent_iteration2_alliance_evidence.md:114`). The Good Inside research also distinguishes app–parent from parent–child relationships (`docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:58`). The existing `co_parenting` field must not be relabeled as parent-child alliance, and neither a child's agreement with an adult's goal nor completion of a requested task is evidence of therapeutic-style task/goal agreement. The no-score restriction stands regardless of a competitor describing its score as reflective rather than clinical.

### End-to-end trace

1. **Admission:** parent text uses authenticated `/chat`, rejects a mismatched claimed user and applies rate limits (`mvp-backend/app/server.py:1120`). The runtime captures the conversation and constructs a user-scoped run (`mvp-backend/app/server.py:482`).
2. **Context:** `_dynamic_context` reads the entire parent-and-child snapshot, prunes empty values and serializes it. It adds saved-item signals, the household roster and ranked content (`mvp-backend/app/agent.py:434`). `_build_system_prompt` injects this as “Family profile,” after the static soul, logistics rules and passive-profiling rules (`mvp-backend/app/agent.py:293`). There is no selector for relevant, reviewed parent context or episode-specific claims.
3. **Extraction:** passive profiling explicitly covers parent work, stress, coping, energy, goals and support. It also instructs the coach to save silently and never mention tracking (`mvp-backend/app/agent.py:272`). `LearnedAboutParent` excludes nulls and calls the shared durable updater (`mvp-backend/app/agent.py:331`). The onboarding agent uses the same schema and updater (`mvp-backend/app/onboarding_agent.py:17`, `mvp-backend/app/onboarding_agent.py:102`).
4. **Persistence:** the updater builds from durable truth in an isolated `ProfilingService`, then saves the family JSON in a transaction (`mvp-backend/app/services/profiles.py:79`). The tool wrapper commits the operation and refreshes the cache afterward (`mvp-backend/app/services/operations.py:195`). Receipts bind user, thread, operation ID and argument digest (`mvp-backend/app/services/operations.py:111`). This is a strong delivery seam, not evidence that a statement is accurate.
5. **Future use:** changing context rebuilds the cached graph on a later `get_agent` call (`mvp-backend/app/agent.py:458`). Updating the profile during a turn does not itself rebuild that turn's system prompt. Retained history can also carry an older interpretation after a field is corrected.
6. **Manual editing:** PATCH changes the process cache before `persist_state` (`mvp-backend/app/server.py:1667`). It lacks the tool path's isolated commit-before-publication sequence and an expected revision. iOS's learned-profile editor sends the parent update and then each child's update separately (`mvp/MVP/ProfileEditorViews.swift:926`). A parent/child pair edited in this UI is not one atomic episode save; an intermediate failure can leave partial updates.

**Important shape problem:** scalars overwrite and lists merge (`mvp-backend/app/profiling.py:6`). `FamilyProfile` holds one parent and a name-keyed child dictionary, not episodes (`mvp-backend/app/profiling.py:153`). Two experiences with different children and contexts can accumulate into one parent strategy list. That is not proof that a strategy generalizes across relationships.

Neither “helps the parent adapt” nor “has reflections/scores” is a defensible unique capability. Do not weaken the no-score contract to mimic a competitor. The implementation hypothesis worth testing is whether a short, attributed episode plus correction-safe continuity and private parent context adds useful help with less burden than these alternatives. The Good Inside review did not locate a published controlled evaluation of GiGi or the complete app; this is a limitation of its search, **not proof none exists** (`docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:52`). Evidence for a parenting mechanism, clinical interpretation, shipped feature and measured product outcome must stay separate. The competitor report's COS-P, CPS, TIK and INSIGHTS comparisons concern specific programs, populations and delivery conditions; they do not validate an AI adaptation (`docs/next-level/iteration-2/research/parent_iteration2_competitors.md:51`). No efficacy or superiority claim follows from this code audit.

The provisional flow is **describe a moment → consider alternatives → choose one parent adjustment → optionally rehearse → try or skip → reflect**. Include ordinary joyful moments with nothing to fix. “No room today” may end at support or no action. No step should require the child to become quieter, comply, or reassure the parent to count as useful to the parent.

The full research adds a necessary boundary-appraisal step within “consider alternatives”: ask what genuinely needs to stay safe or predictable and whether the adult's expectation is realistic or nonessential. Do not preserve a rule simply because the adult set it (`docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:19`, `docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:124`). Repeated frightening conduct, abuse or immediate danger cannot be reframed as another routine experiment; reflection must not delay appropriate human help. Repair neither erases repeated harm nor requires the child to forgive or regulate the adult (`docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:35`, `docs/next-level/iteration-2/research/parent_iteration2_good_inside.md:128`). These are design constraints from the supplied research, not a claim of a validated safety system in the existing code.

## Minimal paired episode contract — proposed

One episode is sufficient for an initial experiment. Do not create an ontology of child types or a psychometric assessment. Stable parent preferences may be reused separately if the parent still considers them current; an episode's temporary exhaustion should not automatically overwrite a standing preference.

| Element | Minimal contract |
|---|---|
| Identity and owner | Server-assigned immutable `episode_id`; authenticated `owner_user_id`; stable child subject ID scoped to that owner; revision and schema version. A child is a subject of a parent's account, not an authenticated participant. Names are display data. |
| Situation | Brief parent-reported setting and approximate occurrence time, allowing “unknown.” Recorded time is distinct from occurrence time. Exact location is unnecessary. |
| Source statements | Stable statement IDs; text; reporter; subject; source kind; optional source-message reference or parent-approved excerpt. Kinds distinguish parent self-report, parent observation, parent-reported child words, parent interpretation and coach hypothesis. |
| Parent side | Optional statements about capacity/constraints, noticed cues, interpretation, response, and a boundary they meant to hold. Keep the parent's intended boundary separate from its stated purpose and any reflection that it may be unrealistic or need revision. Missing, uncertain and declined are distinct from “none.” Do not require personal history or mental-health disclosure. |
| Child side | What the parent saw/heard, and any safely volunteered child perspective the parent chooses to report, with that attribution. Do not ask the parent to elicit a rating, agreement or reassurance from the child. An inferred feeling or motive is a separate hypothesis, never upgraded to fact by saving. This parent-only contract creates no direct child collection flow. |
| Sequence | A short ordered list referencing statements: what happened, what the parent did, what they reported happened next. Temporal order is not causality. Avoid losing the sequence by splitting it into unrelated profile lists. |
| Reflection | Zero or more tentative reflections, each referencing supporting and conflicting statement IDs, stating uncertainty in words and awaiting parent review. Optional dimensions below have no total, ranking, percentile or numeric confidence. |
| Next step and follow-up | Optional action chosen by the parent, feasibility constraints and stop/skip choice. Optionally store parent-approved rehearsal wording, kept distinct from something actually said. Follow-up stores parent-reported action, effort/feasibility and observed response separately; never equates child compliance with success. |
| Review and retention | Review state separate from memory choice: proposed/reviewed/needs-review versus session-only/remember. “Reviewed” means faithful to the parent's account, not independently verified. Correction creates a new revision; forgetting removes content and invalidates derivatives. |

Do not accept `owner_user_id` from model arguments. Validate episode, child, statement, source and revision references under the same owner inside the write transaction. Existing reference checks cover planning IDs, not these proposed resources (`mvp-backend/app/services/operations.py:144`). Treat message text and external references as data, not permission to change owner, retention or tool behavior.

**Optional reflection dimensions: original design prompts, informed by the supplied science but not validated items** (`docs/next-level/iteration-2/research/parent_iteration2_alliance_evidence.md:150`):

- Capacity and available support: what the parent says they could manage in that moment.
- Interpretation: what the parent thought was happening, with alternative possibilities left open.
- Self-regulation and response: what the parent noticed and did, including choosing to pause or seek help.
- Responsiveness: a reported cue and how the parent responded; not a score for attunement.
- Boundaries: the limit the parent intended, its purpose and justification, whether it needs reconsideration, how it was expressed, and what remained difficult.
- Rupture and repair: whether the parent describes a disconnection, any repair they attempted, and the reported response or lack of information. No obligation for the child to forgive or comfort the adult.

These dimensions may overlap; they must not be mandatory questions or progress meters. A missing report is not a deficit. Different situations can support different reflections without one canceling the other. A parent's account is not direct access to the child's experience or the other parent's account. Evidence concerning repair or connection remains a dated, attributed account of words/actions: seeking company, declining a conversation, or a parent's report that they felt closer. None on its own establishes relationship quality. Do not reward pleasing, quietness, compliance, affection on request or reassuring the parent as “connection.”

### Synthetic episode illustrating the distinction

Parent report: “After a long shift, Rowan said, ‘I want to finish building.’ I thought they were ignoring me and raised my voice. Later I said I was sorry for shouting and that we still needed to leave. Rowan did not want to talk then.”

| Episode component | Representation |
|---|---|
| Capacity | Parent self-report: after a long shift. Tiredness is not inferred unless reported. |
| Child words | Parent-reported quote about finishing building. No claim of direct child verification. |
| Interpretation | Parent thought they were being ignored. Do not store “Rowan ignores the parent.” |
| Parent response | Parent reports raising their voice. No global “dysregulated parent” label. |
| Boundary | Parent reports that leaving was still necessary; the reason is not supplied. Ask what made the timing necessary and whether it could reasonably change. Neither automatically drop nor automatically endorse the limit. |
| Repair | Parent reports apologizing for shouting; Rowan did not want to talk then. Do not mark repair accepted or relationship improved. |
| Tentative reflection | “There may have been a mismatch between needing to leave and wanting to finish. We only have your account of this moment.” Link to the relevant statements. |
| Optional parent action | “Would a short pause before restating the limit be manageable next time?” Parent may choose a different step, ask only to be heard, or decline. |
| Follow-up | “I paused and spoke more quietly; leaving was still hard.” Preserve both reports. No alliance score, no causal attribution, no failure assigned to either person. |

## Reuse boundaries and persistence behavior

**Keep:** trusted tenant/run context, atomic operation receipts, commit-before-cache publication, serialized conversation ownership and family cleanup fencing (`mvp-backend/app/agent_runtime/context.py:1`, `mvp-backend/app/services/operations.py:111`, `mvp-backend/app/agent_runtime/service.py:199`). Preserve the distinction between one tool-call replay and a new operation. Add a client action ID for retried review/correction actions and an expected episode revision for stale-editor conflicts.

**Replace:** separate `LearnedAboutParent`/`LearnedAboutChild` calls as the persistence unit for one interaction. A proposed `ProposeEpisode` command should save the source-attributed pair atomically. Parent review, correction and forgetting should use the same service from chat and editors. Avoid a sequence that saves the parent half, fails saving the child half, then claims the episode is complete. Command names here are proposals, not existing APIs.

**Narrow:** `_dynamic_context` should select current, owner-scoped, appropriately reviewed statements, preserve reporter/uncertainty labels, and include only relevant parent context. A parent's correction must outrank old model summaries and trigger re-review of dependent interpretations. A new revision/cache key alone cannot make retained checkpoint history forget an old statement.

**Do not inherit retention accidentally:** `append_transcript` stores role/content JSON and exports snapshots (`mvp-backend/app/agent_runtime/durability.py:18`). Parent voice has a separate retained transcript (`mvp-backend/app/parent_convai_endpoint.py:233`). The current transcript projection lacks stable message IDs in each appended entry (`mvp-backend/app/agent_runtime/durability.py:34`); a future evidence link must not use mutable list position as identity. Capturing evidence also needs an explicit choice between retaining a minimal approved excerpt and retaining the raw conversation.

**Selective forgetting is new work:** current child removal is a name-based profile/child-agent cascade (`mvp-backend/app/server.py:1700`), not an episode/evidence purge. Family deletion provides useful fence and cleanup machinery (`mvp-backend/app/server.py:2471`, `mvp-backend/app/checkpointing.py:407`), but its `ok` response can precede completed snapshot/checkpoint cleanup (`mvp-backend/app/server.py:2535`, `mvp-backend/app/server.py:2550`, `mvp-backend/app/server.py:2566`). Episode forgetting needs its own verified dependency cleanup and honest pending/completed state. Keep minimal tombstones/IDs as necessary to block resurrection; do not retain forgotten prose in a tombstone, receipt or “audit” explanation.

**Parent-private is the default:** an episode belongs to the reporting parent's account. Another parent's account discussing the same child has no automatic access or merged truth. Household/Circle membership is not permission to read private reflections. Voice callback auth still trusts a provider-secret-authenticated `user_id` in the extra body (`mvp-backend/app/parent_convai_endpoint.py:68`); bind the callback to an authorized session before reusing it for episodes. The first text-only local contract does not need voice.
